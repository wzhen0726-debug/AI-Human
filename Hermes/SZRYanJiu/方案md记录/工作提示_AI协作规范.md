# 工作提示（AI 协作规范）

**来源**: 用户明确要求，2026-08-25
**适用范围**: 数字人管线所有环节，以及任何多步流程的 AI 协作

---

## 提示 1：错误处理 — 先找根因，再决定动作（最重要）

> 出现错误时，**不要先想着修改错误**，而是先判断**流程中错误产生的原因**，再尝试在**保证流程正常推进**的情况下，**从源头避免错误**。如果不能避免，再**找我做取舍**，或者开始正式修复错误。

**执行顺序**：
1. **定位根因，不改表象** — 错误在哪一步？是本步逻辑错，还是上游输入就错了？用数据/日志/可视化确认，不凭猜测改。
2. **判断能否从源头避免** — 若是流程设计缺陷（测试污染交付文件、坐标空间约定不一致），改流程/约定，不是每次事后补救。源头修复 = 这类错误以后不再发生。
3. **无法避免 → 找用户取舍** — 多个修复路线各有代价时，列清楚选项和代价让用户选，不擅自选重方案直接做。
4. **正式修复** — 确认路线后从源头修，并验证整条流程能正常推进（不只修这一个点）。

**禁止**：看到姿态错就清零、看到朝向错就转一下、报错就打补丁绕过——这些都是改表象。

**本项目实证**（2026-08-25）：
- 眼珠虹膜朝下 + 打开自带姿态 = 同一根因：测试的 pose 残留被保存进交付文件，头骨前倾把眼珠带歪。
- 正确修法：交付文件保持 rest pose + 保存前姿态纯净检查，测试在临时副本做。

## 提示 2：交付文件永远干净

- **交付文件（_final / 定案版）必须保持 rest pose、无测试残留、无标记点**。
- **验证/测试只在临时副本上做**，测完即弃，不写回交付文件。
- 保存交付文件前做纯净检查（姿态是否单位变换、是否混入临时对象）。

---

## 提示 3：该用的工具要用

- 用户已购/已装的插件（如 Auto-Rig Pro、Quad Remesher、Better FBX），**先评估它能不能解决当前问题**，再决定是否手写。
- 不用它要有明确理由（如无法脚本化、会破坏已定案的上游），并**告知用户**，让用户取舍。
- 不要因为"已经手写了一半"就拒绝换更好的工具。

---

## 提示 4：记录及时、完整、真实

- `方案md记录` 目录是最重要的记录目录，**及时更新**。
- 不只记正确内容，**踩的坑、顽固的错误、失败尝试**都要记。
- 数据必须实测，不拍脑袋（如关节位置用几何测量，不写死猜测值）。

---

## 提示 5：面向不懂建模的人

- 交付物（文档/演示文件）要考虑外行：默认材质预览、移动工具、中文提示、打开即用。
- 打点/标记类操作给**唯一、无歧义的体表标志**（如"三角肌中点"不是"连接处"），配参考图。

## 本项目常用命令速查

```
# Blender 5.1 无头运行
"D:/Program Files/Blender Foundation/Blender 5.1/blender.exe" -b --python <script.py>

# 低优先级（防卡用户机器）
nice -n 19 "D:/Program Files/Blender Foundation/Blender 5.1/blender.exe" -b --python <script.py>

# 骨骼绑定完整重做（见 05骨骼绑定/README.md）
```

**Blender 5.1 API 注意**（历史踩坑）：
- `bpy.context.scene` 不是 `bpy.scene`
- EEVEE 枚举 = `'BLENDER_EEVEE'`
- OBJ 导入 = `bpy.ops.wm.obj_import()`
- 无 `export_texture_compression` 参数
- 后台 `-b` 保存视口状态不可靠，需带窗口模式
