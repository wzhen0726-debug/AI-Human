## 〇、2026-09 死路全记录（弯路本身是资产）

### 死路1：normalize_rest（骨架rest朝向归一化）→ 骨骼断裂错位
- **思路**：把我们骨架的 rest 朝向改成与 Mixamo 完全一致，之后动画可以**直接复制局部旋转**，数学最简单。
- **实现**：编辑模式断开全部 use_connect → 逐骨 `eb.matrix = Translation(head) @ tgt_q`（保头位置）→ **不恢复连接**（脚本注释写"恢复会把子骨头拖回父骨tail，破坏打点位置"）。
- **表面结果**：朝向残余 0.000°、头位置 0.000mm、网格 0.000mm 变形，三项自查全 PASS，动画播放看起来也对。
- **实际后果**（用户两轮 GUI 实测才发现）：
  - 41 根 use_connect **全部变 0** → 编辑模式选大臂移动，肩/小臂不跟随，**所有骨骼各自独立**
  - 每根骨 tail 甩向 Mixamo 方向，但**我们模型腿是岔开的、Mixamo 演员腿接近垂直** → tail 甩离我们自己的关节：膝 52.6mm、踝 56.8mm、肘 48.8mm
  - 03_骨骼绑定（normalize 前）完全正常，问题只在 04_动作测试 → 一度误判为"动画/蒙皮问题"
- **误判记录**：我曾判定"Mixamo 官方骨架本身就 use_connect=False 且有间隙，这是标准布局不是 bug"。**用户直接反驳"我亲眼去看的，都是重叠且完整连接"——用户是对的**。实测 T-Pose.fbx：65 骨中 32 对父子 tail==head 完全重叠，膝/踝/腕/脊柱全部 use_connect=True 且 0.0000mm。有间隙的只有 Hips→UpLeg、Spine2→Shoulder、Hand→指骨这类**解剖上本来就不连续**的位置。教训：**不要用局部观察推翻用户的直接观察，先做完整定量对比**。
- **正解**：见「rest 补偿重定向」（下文技术要点）。骨架结构/连接/权重完全不动，动画用数学换算。normalize_rest.py 已删除。

### 死路2：CYCLES 修改器铺动画周期
- **思路**：行走动画只有 36 帧，想循环播放就用 F-Curve 的 CYCLES 修改器外推。
- **后果**：四元数通道**不能独立循环外推**（q 的四个分量各自周期化 ≠ 旋转周期化）→ 模型在某些帧整体扭曲。
- **正解**：显式复制关键帧铺周期，或干脆按参考帧数原样（最终采用后者）。

### 死路3：欧拉角规避四元数抖动
- **思路**：四元数插值出现抖动（相邻帧 q 与 -q 是同一旋转，插值走长弧），改用欧拉角。
- **后果**：手指卷曲接近 90° 时**万向锁**，手指骨出现 180° 跳变。
- **正解**：回到四元数 + **逐帧符号连续化**（与上一帧点积 <0 就取反）。

### 死路4：逐帧烘焙世界矩阵重定向
- **思路**：算出每骨每帧的世界矩阵，再反解局部旋转写回。
- **后果**：需要自维护整条世界旋转链（`pb.matrix` 设父骨后读回有 stale 问题），根骨 rest 旋转漏算一次就导致角色蹲伏、脚悬空 28cm；参考骨架带 0.01 缩放，`H_r.inverted() @ ref_w` 结果被放大 100 倍。
- **正解**：rest 补偿重定向（每骨一个常量四元数 C，逐帧只算参考的世界增量）。

### 死路5：rim 倒角权重机制（眼周锐化）
- **思路**：眼睑缘加小倒角 = 制造硬边 → QR 的 AutoDetectHardEdges 识别折角 → 低模沿眼睑缘布线 → 烘焙后眼睑缘锐利。
- **隐藏 bug**：`rim_pre_sharpen.py` 先写 `bevel_weight_edge` 属性、后执行 `bm.to_mesh(me)`，**属性被整个冲掉**（to_mesh 重建几何数据层）。结果 BEVEL 修改器挂着、权重全 0 = 空转，**静默失效数月无人发现**（因为脚本打印"已保存"、修改器也在，没人查属性值）。
- **连锁后果**：高模无硬边 → QR 没沿眼睑缘布线 → 低模**根本没有 rim 边环**（实测 72 个轮廓点附近只有 39-40 条散边、断成 5~6 段、轮廓到边最大距离 5.9mm）。
- **补救尝试A（带宽法）**：`rim_bevel.py` 用"边中点距轮廓 <3mm"选边 → QR 低模眼部边长中位就有 ~3mm，抓到 **2~3 排交错碎边共 138 条**（散布 0.56~3.0mm），眼周碎线全带上倒角权重。用户 GUI 一眼看到。
- **补救尝试B（只查距离的最近边法）**：每个轮廓点取点-线段最近边 + 自适应紧阈值（0.4×边长中位）→ 138 降到 25 条，但其中 **14 条切向角 44~77°**，是横穿眼睑轮廓的斜边。retopo 布线不与特征轮廓对齐，"最近"≠"顺着"。
- **补救尝试C（距离+切向双条件）**：加"边方向与轮廓切向夹角 <35°"过滤 → 14 条全顺着轮廓（切向角 2.8~31.8°，距轮廓 ≤0.91mm），数值自查 ALL PASS。
- **用户终判**：GUI 复核后仍判定"明显没有任何存在的必要"——14 条还是不成圈的散短线段（6 段），既不连续也无实际锐化效果，只剩视觉噪声。**整套机制删除**（rim_pre_sharpen.py + rim_bevel.py + 01a/02 对应步骤），02 直接吃眼窝高模，03 主动剥离 bevel/crease 属性。眼睑缘锐利度改由烘焙法线贴图从高模获取。
- **教训**：①数值全过 ≠ 用户满意，边级属性改动必须预期用户 GUI 复核一轮；②做"沿特征线加倒角权重"前先验证**特征边环是否存在**（连通分量是否≈闭合环），无环时任何选边法都只能抓碎片，不如不做；③静默失效的 bug（脚本成功、修改器在、但属性被冲掉）最危险，**自查要读属性实际值而不是查对象是否存在**。

## 二、各阶段技术要点

### 01 高模修复
- 做对：foot_score v3 朝向修复、Taubin 平滑、焊接必须早于UV。
- 做错：法线修复前烘焙 = 黑面（08-24 三次返工）；命门是面还 flat 时调 add 固化平直法线。
- 局部几何异常先诊断根因再修；胸口凸起是原始几何特征需雕刻平滑，不是法线问题。

### 01A 眼窝与眼球
- 眼窝定案：v48 inward_fillet（M形凸脊根因=倒角环外扩段，只内收不下沉）。
- 眼球定案：v4 解剖规律（角膜凸0.1mm/虹膜底+1.4mm），半自动微调面板。
- 用户GUI手动调→脚本定量反推解剖规律固化 = 审美定案最快路径。

### 02 QR 拓扑
- 输入必须焊接（remove_doubles 0.0001）+ 填开放边，否则 xremesh 卡死。
- SymAxis 关闭决策：纹理不对称导致烘焙错位。
- **FBX 导入残留微旋转**：xremesh 输出 FBX 经 Blender 导入后对象带 `-1.629e-7 rad`（**-0.000009°** X 轴旋转，轴向转换浮点残差），会被下游一路继承。导入后立即 `transform_apply(rotation=True)` 归零（顶点位移 ~0.3 微米）。
- **rim 倒角机制已整套删除**（见死路5）。眼睑缘锐利度由烘焙法线贴图从高模获取，不需要在低模上做几何倒角。

#### 02-09 定案：眼窝独立材质引导（UseMaterialIds），关掉角度检测硬边 + 法向分割
两轮迭代得到。第一轮用户 GUI 实测插件面板提出：默认"通过角度检测硬边"(AutoDetectHardEdges=1) 抹平结构，改勾"使用法向分割"(UseIndexedNormals=1) 能保结构 → 实测证实（B 组）。第二轮用户进一步提出：给眼窝做独立材质、QR 勾"使用材质"(UseMaterialIds=1) 并**取消其他两项** → 实测 D 组全面最优，定为最终方案。

# 01a: 眼窝碗面赋独立材质(输出 _qr.blend, 不动烘焙源文件), 皮肤保持原材质
# 判据(修正后): XZ投影在rim轮廓内 且 3D距rim折线 < 该眼rim bbox对角线(≈37mm自适应尺度)
#   → 材质边界(碗/皮肤公共边)正好=眼睑缘rim, 距rim中位0.077mm/max0.300mm
# 02 settings: UseMaterialIds=1 / UseIndexedNormals=0 / AutoDetectHardEdges=0

##### ⚠⚠ 判据漏掉前后深度(Y) → 后脑勺面被误判成眼窝（真 bug，已修，曾污染主产物）
第一版判据**只用 XZ 投影做 point-in-polygon**，没有约束 Y（前后深度）。后果：后脑勺的面（y=+82~98mm）在 XZ 投影上恰好落进眼裂的 XZ 范围（x[-52,52] z[1664,1676]），被误赋 EyeSocket 材质。

实测污染规模：**350 个"眼窝"面里 136 个（38.9%）在后脑勺**，距 rim 204mm（真碗面 y=−115~−98mm）。

危害（正是用户反馈"02QR 效果还是不太好"的成因之一）：QR 被后脑勺那圈**假材质边界**引导布线——材质边界连通分量从理想的 2 个环（L/R 眼各一圈）变成 4 个环，多出的 2 个假环扰乱整体拓扑；且高模上真碗面 3,304 个，QR 却只分出 350 个（假边界挤占了真眼窝的分区）。

定位过程（值得记）：第一版验证脚本报"材质边界边距 rim 中位 189.87mm"，与"350 个眼窝面全在眼区盒内"直接矛盾。逐层下钻（`_dbg_coord`→`_dbg_coord2`→`_dbg_coord3`）才发现：**① 我的验证脚本自身有 bug**（bmesh 访问 `e.verts[i].index` 前漏了 `verts.ensure_lookup_table()`，读到过期索引 → 取错顶点 → 假的 189mm；② patch 时丢过一行 `bound.append()` 导致边界边恒为 0）。修掉验证脚本 bug 后，才看清真正的数据：最远的 103 条边界边中点**全部在 y=+98.5mm（后脑勺）**，而 rim 在 y≈−107mm——相距 204mm，方向相反。**判据缺 Y 约束**这个根因这才浮现。

修复（测量驱动，不硬编码阈值）：
```python
# bbox 粗筛先加 Y 深度约束(rim的Y ± rim对角线*0.5), 滤掉后脑勺
# 决定性判据: 3D 距离(不是XZ投影) — 到所属眼 rim 闭合折线的最近距离 < 该眼 rim bbox 对角线
#   真碗面 ≤22mm 通过; 后脑勺面 204mm 被干净排除; 阈值随头型自适应(非固定值)
```

修复后实测：

⚠ **教训**：用投影（2D）判 3D 归属，必须检查被投影掉的那个轴有没有歧义。人脸模型前后都有面落在眼裂 XZ 范围内——这不是边角情形，是 38.9% 的主体污染。以后凡是"落在某轮廓内"的判据，先问：沿被丢弃的轴，还有谁也会落进来？

**验证脚本自身的坑（同源教训）**：bmesh 里访问 `e.verts[i].index` 前必须 `bm.verts.ensure_lookup_table()`（只 ensure edges 不够），否则读到过期索引、取错顶点，报出与事实矛盾的数字。当验证结果与其他已确认事实矛盾时，**先怀疑验证脚本，再怀疑被验证对象**——但两者都要实测，不能靠推理定案。

##### ⚠⚠ 补：加了 Y 深度后**仍溢出到上眼睑/眉部** → 第三判据维度"rim 平面内侧"（真 bug，已修）
Y 深度判据只滤掉了后脑勺（y=+82~98mm），但**上眼睑/眉部皮肤**（y 与碗面接近）的 XZ 投影同样落在 rim 轮廓内、距 rim 仅 1.71mm（远小于 37mm 对角线阈值），照样被误赋材质。用户看图反馈"很多地方有材质溢出"，但 vision 只报出 1 个孤立红点——**vision 漏报，必须定量**。

实测溢出规模：**413/3304（12.5%）**，全部在上眼睑/眉部（z≈1675.8、y=−115，比 rim 平面更靠前）。

关键证据（决定性）：溢出面相对 rim 平面的有符号深度**全为负**（−5.31~−0.01mm），真碗面**全为正**（+0.01~+18.24mm），**零重叠**——而原判据只有"3D 距 rim < 37mm"，溢出面距 rim 才 1.71mm，全被放进来了。

修复（第三判据维度）：
```python
# SVD 分眼拟合 rim 平面 → 单位法线指向脸前方(-y)
# depth = (面中心 - rim平面中心) · (-法线)   >0=碗内侧(眼球方向)  <0=外侧(眼皮/额头皮肤)
# 判据: depth ≥ -TOL 才算碗面;  TOL = rim对角线 × 0.15%（≈0.056mm，只吸收平面拟合噪声）
```
⚠ **TOL 不能设松**：曾误设 0.8%（=0.3mm），会让上睑缘溢出面（depth −0.3~−0.01mm）漏网——那正是用户肉眼可见的红色溢出。因真碗面与溢出面分界**零重叠**（都在 ±0.01mm 内），容差可以收到几十微米级。

修复后溢出 **413（12.5%）→ 0（0.00%）**，视觉终验红色干净箍在眼窝内、眼睑/眉部无溢出。

⚠ **诊断脚本必须与生产脚本同源**：我的核查脚本一开始用**全局单一平面**（两眼 rim 合并 SVD 拟合），报 37 个"溢出"depth 到 −0.57mm，与 assign 的"0 溢出"矛盾。原因是全局平面会把"在自身眼平面内侧、但在两眼平均平面外侧"的 rim 缘面误判为溢出。对齐到**分眼平面**后真溢出 = 0。**验证脚本的判据要照抄生产脚本，不能另写一套"差不多"的**——否则验证本身制造假阳性，浪费一轮排查。

#### 05-09 动画重定向定案 v4：03B 标准化 rest + 增量公式 + Hips 完整三轴搬运
逐帧公式（每骨 b，父骨 p）自 v3 起未变：
```
D_b(t) = R_ref_rest_b^-1 @ W_ref_b(t)        # 参考骨相对自身rest的世界旋转增量
q_b(t) = A_b^-1 @ D_p(t)^-1 @ A_b @ D_b(t)   # 写入我们骨骼的局部四元数
A_b    = R_our_rest_p^-1 @ R_our_rest_b      # 我们骨架的rest相对朝向, 根骨 parent=identity
```
推导依据：Blender 链式公式 `W_b(t) = W_parent(t) @ R_rest_parent^-1 @ R_rest_b @ q_b` 在世界空间成立。

**v4 的关键变化：rest 不再是"保持自身"，而是先由 03B 标准化到 Mixamo T-Pose。**
03B 之后 `R_our_rest ≈ R_ref_rest`（实测 55 骨完整旋转差 max=0.0008°），所以 `C = R_our^-1 @ R_ref → 单位矩阵`，增量公式**自动等价于绝对朝向匹配** —— 而且不会重演 v2 的内八/猫步。

为什么这次安全、v2 不安全（同一件事，差别全在网格）：

| | v2（错） | **03B（对）** |
|---|---|---|
| 骨骼 rest | 运行时靠 `C` 补偿扳直 | rest 层面一次性重摆 |
| **网格** | **不动**（仍是岔开的站姿） | **LBS 跟随重摆**（与骨骼始终匹配） |
| 后果 | 蒙皮在岔开网格上被向内硬挤 → 内八/猫步 | 骨骼与网格同步，无扭折 |

v2 的病根从来不是"对齐参考"本身，而是**只扳骨骼不扳网格**。

##### ⚠ 猫步有**两个独立根因**，只修一个不够（实测教训）
| 根因 | 症状 | 修复 |
|---|---|---|
| ① v2 的 `C` 绝对朝向补偿 | 大腿被扳垂直（8.18°→0.35°）、踝从 ±143mm 收到 32~75mm | v3 去掉 C；v4 改为 03B 在 rest 层面对齐（网格同步） |
| ② **retarget 只搬 Hips 垂直 z** | 丢弃参考的**左右重心侧移**（实测 Hips x 摆幅 41.6mm、y 摆幅 57.0mm，我们 0.0mm）→ 落地脚被拉到离中线 **9.6mm** | Hips **完整三轴搬运**，用雅可比逆把世界位移转回局部 |

根因 ② 是被 03B **暴露**出来的：之前 v3 靠"保留 8° 外八 rest"把脚撑在 143mm，掩盖了侧移丢失。腿一摆直，猫步立刻现形。
搬运安全性已实测：三个动画的 Hips **首末差均 = 0.00%**（纯周期摆动 walk-in-place），完整搬运不会让角色飘走。

位移缩放要**分轴**（不能用一个比例套三轴）：
- 左右侧移 → **骨盆宽比** `our UpLeg|x| / ref UpLeg|x|` = 0.8935
- 垂直/前后 → **腿长比** `(our hips_z − our foot_z)/(ref …)` = 0.9634
用腿长比缩侧移会把 Hips 搬过头，落地脚被拉向中线（实测 R 腿着地踝只剩 24.2mm）。

##### v4 金标准（写进 retarget 自查，防回归）
1. **增量一致**：`D_ours(t)` vs `D_ref(t)` 夹角 ≈0 — 实测 14 骨全 0.000°
2. **完整旋转对齐**（v3 只查骨向是错的）：55 骨 axis-angle 差 <0.5°，**单独报 roll 分量** — 实测 max=0.0008°（roll 0.0006°）

##### LBS 网格重摆的两个坑
1. **ARP 蒙皮权重未归一化**（实测 Σw 中位 0.9828、min 0.897，91,523 个顶点 |Σw−1|>0.01）。Blender 的 Armature 修改器默认 `vertex_group_normalize=True`，所以必须**归一化**才能复现其行为。
   错用 `Vn += (1−Σw)·Vw` 补偿（等于把权重缺口当作"绑定到世界原点"）会让每顶点被往原位拉 1.7~10%，在旋转 8° 的长骨上是毫米级错位 → 边长 max 变化 167%、bbox 深度 +14.9%。
2. **"网格边长不应变化"是错误判据** —— 03B 的目的就是改变姿态（外八 A 字 → 标准 T-Pose，Shoulder 要转 21°、手臂要摆平），边长/bbox 变化是**预期结果**。拿"不该变形"去卡"就是要变形"的操作，判据与目标自相矛盾。
   正确判据是**刚性区检验**：归一化后单骨独占（>0.9999）的顶点必须严格刚体变换（实测边长变化中位 **0.0000021%**、p99 0.000037% = 机器精度，证明 LBS 实现正确）；跨骨混合区的涂抹是 LBS 固有（实测最重在手指 Pinky1 59%、Shoulder 50%，等价于在 pose 模式摆同样姿势），只报告不判 FAIL。
   ⚠ 判"单骨独占"必须用**归一化后**权重：原始 `dom_w>0.9` 在 Σw=0.897 时归一化后有效权重达 1.059 且两端次骨混入不同 → 仍有相对位移（实测 p99=5%），判据失效。
   另：性能上 LBS 要**按骨批量向量化**（55 次 einsum），逐权重条目循环 35.6 万次要十几分钟。

##### 曾经的错误做法 v2：加 rest 补偿常量 C（绝对朝向匹配）→ 内八/猫步
v2 曾加 `C_b = R_our_rest^-1 @ R_ref_rest`，令 `D' = C @ D`，使我们的**绝对世界朝向逐帧等于参考**（当时自查 36帧×14骨 全 0.000°"通过"）。
**这是错的**——它只扳骨骼不扳网格。实测两者 rest 差异巨大：

| | 我们 | Mixamo 参考 |
|---|---|---|
| 大腿外展 | **8.18°**（岔开） | 0.35°（近乎垂直） |
| 脚掌外八 yaw | **+9.37°** | +1.53° |
| 踝离中线 | **±142.9mm** | ±91.2mm |

C 补偿后：大腿被扭垂直、脚被扭正直、踝从 ±143mm 收到 32~75mm → 网格在自己岔开的 rest 上被向内扭 → **用户看到的"内八感 + T台猫步"**。

**教训（比公式本身重要）**：① 绝对朝向匹配 ≠ 动作正确，除非网格同步重摆（这正是 03B 的做法）。② **自查标准本身可以是错的** —— v2 用"世界朝向与参考 0.000° 一致"当金标准，所以错误方案能"全部通过"；v3 的"rest 保持 ≠0"同样在 v4 变成拦路虎。金标准必须验证用户真正关心的属性（腿是否自然、脚是否跨中线、骨骼与网格是否匹配），而且**方案一改就要重新审判据**。

##### action 帧范围坑
只设 `act.use_frame_range=True` 而不设 `frame_start/frame_end` → `act.frame_range` 恒为 `[1,1]`，任何按它遍历的脚本**只跑 1 帧**（诊断时误以为动画只有 1 帧）。必须显式 `act.frame_start, act.frame_end = fstart, fend`；诊断脚本可用遍历 fcurve keyframe_points 求真实范围兜底。

其余坑（沿用）：参考 rest 用**每个动画 FBX 自带的绑定姿势**（腿长比逐个实测：Walk 0.944、Running/Jump 0.882）；四元数逐帧符号连续化；5.x 不要显式 `slots.new(id_type='ARMATURE')`；Hips 只重建垂直起伏且垂直轴探测必须在绑动画前；只有行走要求全程贴地（跑/跳本来有腾空相）。

#### 05-09 骨骼连通的定量判据（回答"Mixamo 到底连不连"）
实测 T-Pose.fbx 参考骨架（65 骨）：
- **32 对父子 tail==head 完全重叠**，变形链关节全部 `use_connect=True`：膝 0.0000mm、踝 0.0000mm、腕 0.0000mm、脊柱 0.0000mm
- 有间隙的是**解剖上本来不连续**的位置：Hips→UpLeg、Spine2→Shoulder、Hand→各指骨、Neck→Head、Head→HeadTop_End
- 我们 03_骨骼绑定：41/55 连接、13/55 有间隙（全是上述解剖间隙）= **健康**
- 判据：`use_connect` 数 + 变形链关节 tail-head 距离。只看"有没有间隙"会误判（解剖间隙是正常的）。

## 三、Blender 5.1 API 高频坑

| 坑 | 正确写法 |
|---|---|
| `bpy.ops.object.add` 建在3D光标处 | 先 `scene.cursor.location=(0,0,0)` |
| `ShrinkwrapConstraint.wrap_method` | `shrinkwrap_type`，枚举 `NEAREST_SURFACE` |
| `mesh.vertices[::50]` 切片 | 不支持，按索引遍历 |
| `action.fcurves` | 5.x 不存在，用 `layers[].strips[].channelbags`（属性带s不可调用） |
| `ActionSlot.name` | 无此属性，用 `identifier`/`handle` |
| `scene.cursor_location` | `scene.cursor.location` |
| 后台 `-b` 模式 select_all 失效 | 用数据API `o.select_set` + 先 mode_set('OBJECT') |
| 插件噪音淹没print | 结果写文件而非靠 stdout |
| `bm.to_mesh(me)` 冲掉刚写的 `me.attributes` | 先 to_mesh → 再写 attributes → `me.update()` |
| `ToolSettings.use_project` / `snap_target_best` | 5.1 已移除，写前 `hasattr` 检查 |
| `tool_settings.snap_elements` | 4.0+ 用此名；旧版 `snap_elements_base`；两者都可能不存在，`try/except (TypeError, AttributeError)` 兜底 |
| `act.slots.new(id_type='ARMATURE')` 给 object 动画 | 槽类型不符 → 赋值 RuntimeError；让 `keyframe_insert` 自动建槽 |
| `bpy.data.actions.remove()` 5.x | 会连带删共享 slot 的副本 → 改用重命名/不复制 |
| 正交视图对准某区域 | `region_3d.view_perspective='ORTHO'` + `ortho_scale`=视野宽度(米)，`view_distance` 在正交下无效 |
| numpy 向量除法广播 | `SD / np.sqrt(l2)` 报 shape 不匹配 → `SD / np.sqrt(l2)[:, None]` |
