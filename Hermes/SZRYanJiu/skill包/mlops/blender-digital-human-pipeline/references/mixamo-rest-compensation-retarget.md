# Mixamo重定向(03B标准化rest) + QR材质引导 + rim倒角死路 (已验证)

## 0. 03B骨骼标准化: rest开度对齐Mixamo T-Pose + 网格LBS跟随 (v4定案)

用户要求把骨骼rest开度重映射到Mixamo标准T-Pose并让它成为新静置姿态(目的: 大腿自然 + 骨骼标准化). 实测55骨**完整旋转差max=0.0008°**.

做完后 `C = R_our_rest^-1 @ R_ref_rest → 单位矩阵`, v3的增量公式自动等价于绝对朝向匹配, **且不会重演v2的内八/猫步** — 差别全在网格:

| | v2(错) | 03B(对) |
|---|---|---|
| 骨骼rest | 运行时靠C补偿扳直 | rest层面一次性重摆 |
| **网格** | **不动**(仍岔开站姿) | **LBS跟随重摆** |
| 后果 | 蒙皮在岔开网格上被向内硬挤→内八/猫步 | 骨骼与网格始终匹配, 无扭折 |

v2的病根从来不是"对齐参考"本身, 而是**只扳骨骼不扳网格**。

### ⚠ 三个真bug(全在实现细节, 每个都会静默产出坏文件)
1. **清理FBX参考骨架绝不能用反向删除白名单** `if o not in (arm,mesh): remove`. 03文件有**41个对象**, 这句删掉39个 — 含Eye002眼球(retarget有`assert 'Head' in vg.name`, 丢了必崩)和37个ARP cs_*自定义形状. 正确: 导入前`pre_objs=set(bpy.data.objects)`, **只删本次新增**。
2. **眼球顶点组名带`mixamorig:`前缀, 骨名不带**(前缀是后续retarget才加) → 按名匹配失败 → 眼球被当"无权重"跳过 → 不跟随Head骨, 与新网格错位27.5mm. 正确: `nm.split(':')[-1]`容忍前缀。凡"按名字关联两套骨架数据"都要查前缀一致性。
3. **写回骨骼必须用`EditBone.matrix`一次性设, 不能`eb.roll=0`+`align_roll()`**. 后者实测绕骨向轴**roll差整整90°**(骨向Y轴差0.000°!). 极隐蔽: 骨向对→head/tail对→网格LBS对→**rest外观正常/渲染PASS**, 只有动画崩(腿自扭转把脚甩到z=+158mm, 参考仅-0.1mm; 脚z摆幅达参考3倍).
   另`use_connect`会干扰matrix设置(设父骨时Blender立刻把父tail拉到**尚未更新**的子骨head, 骨长被拉坏78mm) → **三遍走: 全断开→根到叶设matrix→恢复connect**。

### ⚠ 对齐骨骼必须查完整旋转, 不能只查骨向
自查只比`R[:,1]`(骨向)会让roll差90°报"0.0000°全过". 必须axis-angle比完整矩阵 + **单独报roll分量**。

### LBS网格重摆两个坑
1. **ARP蒙皮权重未归一化**(实测Σw中位0.9828/min0.897, 91523顶点|Σw-1|>0.01). Armature修改器默认`vertex_group_normalize=True`, 必须归一化才复现其行为. 错用`Vn += (1-Σw)*Vw`补偿(把权重缺口当"绑定到世界原点")→每顶点被往原位拉1.7~10%, 旋转8°长骨上毫米级错位→边长max变化167%、bbox深度+14.9%。
2. **"网格边长不应变化"是错误判据** — 目的就是改姿态(外八A字→T-Pose, Shoulder转21°), 边长/bbox变化是**预期结果**。拿"不该变形"卡"就是要变形", 判据与目标自相矛盾。
   正确判据=**刚性区检验**: 归一化后单骨独占(>0.9999)顶点须严格刚体(实测边长变化中位**0.0000021%**/p99 0.000037%=机器精度, 证明实现正确); 跨骨混合区涂抹是LBS固有(实测最重手指Pinky1 59%/Shoulder 50%, 等价pose模式摆同样姿势), 只报告不判FAIL。
   ⚠判"单骨独占"必须用**归一化后**权重(原始dom_w>0.9在Σw=0.897时有效权重达1.059且两端次骨混入不同, 实测p99=5%, 判据失效)。
   性能: LBS要**按骨批量向量化**(55次einsum), 逐权重条目循环35.6万次要十几分钟。

### 眼球等附属蒙皮网格必须一并LBS
只变换最大网格会漏掉眼球(663顶点蒙皮到Head). 凡有ARMATURE修改器+顶点组的网格都要变换, 否则错位。ARP的cs_*是骨骼显示形状(顶点组=0), 不参与。

## 1. Mixamo动画重定向: 增量公式(v3起未变) + Hips完整三轴搬运 (v4定案)

**两条已废弃的错误路线**:
- v1 normalize_rest: 把骨架rest朝向改成Mixamo方向再直接复制局部旋转 → tail甩离自己关节(膝52mm/踝57mm), use_connect全断(41→0) → 编辑模式骨骼各自独立不联动+关节错位。用户两轮发现。
- **v2 C补偿(绝对朝向匹配): 错得更隐蔽** — 骨架结构保住了, 但加常量 `C_b = R_our_rest^-1 @ R_ref_rest` 令 `D'=C@D`, 使绝对世界朝向逐帧等于参考。当时自查"36帧×14骨 0.000°全过", **但用户看出走路内八+T台猫步**。

v2为何错: 它把我们的站姿扳成Mixamo演员的站姿。实测两者rest差异巨大:

| | 我们 | Mixamo参考 |
|---|---|---|
| 大腿外展 | **8.18°**(岔开) | 0.35°(近乎垂直) |
| 脚掌外八yaw | **+9.37°** | +1.53° |
| 踝离中线 | **±142.9mm** | ±91.2mm |

C补偿后大腿被扭垂直、脚被扭正直、踝从±143mm收到32~75mm → 网格在自己岔开的rest上被向内扭 → 内八+脚跨中线猫步。

**正确路线(v3, 实测通过)**: 骨架结构/连接/权重完全不动, **保留自己的rest朝向**, 只叠加参考的运动增量:

- `D_b(t) = R_ref_rest_b^-1 @ W_ref_b(t)` — 参考骨相对自身rest的世界旋转增量
- `q_b(t) = A_b^-1 @ D_p(t)^-1 @ A_b @ D_b(t)` — 写入我们骨骼的局部四元数
- `A_b = R_our_rest_p^-1 @ R_our_rest_b` — 我们骨架的rest相对朝向(根骨parent=identity)

v3效果: 我们的姿态 = 自己的rest站姿 ⊕ 参考的动作。实测大腿外展全程-7~8°(不跨0)、踝离中线≥77mm。
**v4起rest已由03B标准化**, 所以上述"保留自身外八"不再适用(见第0节)。

### ⚠ 猫步有两个独立根因, 只修一个不够
| 根因 | 症状 | 修复 |
|---|---|---|
| ① v2的C绝对朝向补偿 | 大腿被扳垂直(8.18°→0.35°), 踝±143→32~75mm | v3去掉C; v4改由03B在rest层面对齐(网格同步) |
| ② **retarget只搬Hips垂直z** | 丢弃参考**左右重心侧移**(实测Hips x摆幅41.6mm/y摆幅57.0mm, 我们0.0mm) → 落地脚被拉到离中线**9.6mm** | Hips**完整三轴搬运**, 雅可比逆把世界位移转回局部 |

根因②是被03B**暴露**的: 之前靠保留8°外八rest把脚撑在143mm掩盖了侧移丢失, 腿一摆直猫步立刻现形。
搬运安全性实测: 三动画Hips**首末差均=0.00%**(纯周期摆动walk-in-place), 完整搬运不会让角色飘走。

**最重要的教训**: ①绝对朝向匹配 ≠ 动作正确, **除非网格同步重摆**(这正是03B的做法)。②**自查标准本身可以是错的, 而且会随方案演进变成拦路虎** — v2拿"与参考0.000°一致"当金标准所以错误方案全过; v3拿"rest保持夹角≠0(实测7.87°)"当金标准, 在v4/03B下该值必然≈0, 留着等于禁止正确方案。金标准必须验证用户真正关心的属性(腿是否自然、脚是否跨中线、骨骼与网格是否匹配), **方案一改就要重新审判据**。

**v4金标准(已写进retarget自查防回归)**:
1. 增量一致: D_ours(t) vs D_ref(t) 夹角≈0 — 实测14骨全0.000°
2. **完整旋转对齐**(v3只查骨向是错的): 55骨axis-angle差<0.5°, 单独报roll分量 — 实测max=0.0008°(roll 0.0006°)
3. **猫步判据**: 着地相踝离中线 ≥ `参考同侧着地踝min × 骨盆宽比 × 0.75` — 实测L 44.0mm(阈值37.9)/R 24.3mm(阈值20.9)
4. Walk腾空=0帧(跑/跳本就应有腾空相)

⚠**阈值不能硬编码mm值**: 参考自己这个walk左右不对称(L腿着地踝min=56.5mm, R腿仅31.1mm), R腿24.3mm看着小却是等比正确值(31.1×0.894=27.8mm). 基准必须从**参考实测**推导。
⚠判"着地相"不能用绝对`z<0.03`(那是脚部**顶点**地面接触阈值; 踝**骨**在~105mm高处永远不<0.03 → 一个着地帧都匹配不到, **静默退回兜底阈值**)。参考网格已删时用"踝骨z相对该侧周期最低点<40mm"。

**v3金标准(已作废, 留档看判据如何反噬)**: ①增量一致 ②rest保持夹角**≠0**(实测大腿7.87°) ③大腿外展全程同号不跨0 + |外展|≥3° + 踝≥50mm。
判据坑(v3时代有效): 外展角用`abs()`会丢符号致误报(当时我们rest是-8.18°, 负号=向外岔开); 不要用min|az|判"最接近垂直时刻", 要看min/max是否跨0。v4 rest已摆直, 外展角逐帧与参考**差0.00°**, 该判据由③取代。

对比脚本必须防action共享污染(两骨架各绑各的action, `assert our_act != ref_act`)。

坑:
1. 参考rest用**每个动画FBX自带的绑定姿势**(Mixamo各文件角色比例不同, 腿长比逐个实测: Walk 0.944, Running/Jump 0.882)
2. 四元数逐帧符号连续化(与上一帧dot<0取反)防插值长弧抖动
3. Blender 5.x: **不要显式slots.new(id_type='ARMATURE')** — 对object动画数据无效, 赋值RuntimeError「此槽不适合此数据块类型(OB)」。让keyframe_insert自动建槽, 绑槽时try/except RuntimeError跳过
4. Hips搬运要**完整三轴**(不只垂直起伏, 见上"猫步两个根因"). 实现: 绑动画前用单位位移探测**3x3雅可比**(局部轴→世界位移), 逆矩阵把世界位移增量转回局部; 探测必须在绑动画前(有action时pb.location被fcurve覆盖)。
   位移缩放必须**分轴**: 左右侧移→**骨盆宽比**(our/ref UpLeg|x|, 实测0.8935); 垂直/前后→**腿长比**(实测0.9634). 用腿长比缩侧移会搬过头, 落地脚被拉向中线(实测R腿着地踝只剩24.2mm)。
   Mixamo FBX的`obj.scale=0.01`会混进`matrix_local`的3x3 → **取旋转必须逐列归一化**, 否则所有骨假报89.43°差。Blender骨向是局部**Y**轴不是Z。
5. 跑/跳本来有腾空相, **只有行走要求全程贴地**
6. **action帧范围坑**: 只设`use_frame_range=True`不设`frame_start/frame_end` → `act.frame_range`恒为`[1,1]`, 任何按它遍历的脚本只跑1帧。必须显式设; 诊断脚本可遍历fcurve keyframe_points求真实范围兜底。

## 1b. QR结构保留定案: 眼窝独立材质引导(UseMaterialIds), 关掉角度检测硬边+法向分割

默认AutoDetectHardEdges=1会**抹平眼窝棱线**(rim区折角仅35.7°, 远处对照179.6°). 两轮迭代:
用户先提出法向分割(UseIndexedNormals=1)保结构→实测证实(B组); 再提出给眼窝做独立材质+只勾"使用材质"→实测D组全面最优, 定为方案.

配置: `UseMaterialIds=1` / `UseIndexedNormals=0` / `AutoDetectHardEdges=0`.

### ⚠ 用2D投影判3D区域归属必须检查被丢弃轴的歧义(曾污染38.9%面)
识别"眼窝碗面"时只用XZ投影做point-in-polygon → **后脑勺面(y=+82~98mm)的XZ投影恰好落进眼裂XZ范围**被误赋材质. 实测350个"眼窝"面里136个(38.9%)在后脑勺, 距rim 204mm(真碗面y=-115~-98mm).
危害: QR被假材质边界引导布线(连通分量从2环变4环), 扰乱整体拓扑; 高模真碗面3304个但QR只分出350个.
正确判据: **3D距离** — 到所属眼rim闭合折线的最近距离 < 该眼rim bbox对角线(≈37mm自适应, 不硬编码). 真碗面≤22mm过, 后脑勺204mm排除. bbox粗筛也要加Y约束.
**通用规则**: 凡"落在某轮廓内"判据, 先问沿被丢弃的轴还有谁也会落进来. 人脸前后都有面落进眼裂XZ范围, 不是边角情形而是主体污染.

决定性验证判据(衡量QR有没有真沿rim布出边环): rim折线密集采样点→低模最近**边**的3D距离. 修复后中位0.98mm/<1mm占52%; 角度硬边配置1.69mm/26%. 贴合度1.7倍.
⚠不要用"rim区二面角中位数"跨不同密度网格比较(点密→每边转角小), 也不要用max(退化面离群污染).

### ⚠ 材质赋面要三个判据维度, 缺一个就溢出(两轮各发现一个)
识别"眼窝碗面"时:
- **只有XZ投影point-in-polygon** → 后脑勺面(y=+82~98mm)XZ投影落进眼裂范围被误赋. 实测136/350=38.9%在后脑勺, 距rim 204mm. → 加**3D距rim折线 < rim bbox对角线**(≈37mm自适应).
- **加了3D距离仍溢出到上眼睑/眉部** → 那些面XZ在rim内、距rim仅1.71mm(远小于37mm阈值), 但在rim平面**前方**(depth -5.31~-0.01mm), 不是碗内. 实测溢出413/3304=12.5%, 用户看图一眼认出"很多地方材质溢出"(vision只报1个点→漏报, 必须定量). → 加第三维**rim平面内侧**: SVD**分眼**拟合平面, `depth=(P-ctr)·(-n) ≥ -TOL`.
- TOL取rim对角线**0.15%**(≈0.056mm)只吸收平面拟合噪声; 曾误设0.8%(=0.3mm)会让上睑缘溢出面(depth -0.3~-0.01mm)漏网 — 那正是用户肉眼可见的红色溢出. 实测真碗面depth全≥+0.01/溢出面全≤-0.01, **分界零重叠**所以容差可极紧.
修复后溢出413(12.5%)→0(0.00%).
⚠**诊断脚本必须与被验证逻辑同源**: 我的核查脚本用**全局单平面**(两眼rim合并SVD)报37个溢出depth到-0.57mm, 与assign的0矛盾 — 因为全局平面会把"在自身眼平面内侧但在两眼平均平面外侧"的rim缘面误判溢出. 对齐到分眼平面后真溢出=0. 验证脚本的判据要照抄生产脚本, 不能另写一套"差不多"的.

### ⚠ bmesh陷阱: 访问 e.verts[i].index 前必须 bm.verts.ensure_lookup_table()
只ensure edges不够. 漏了会读到过期索引→取错顶点→报出与事实矛盾的数字(曾报假的"距rim 189mm", 实为1.6-5.7mm). **验证结果与其他已确认事实矛盾时, 先怀疑验证脚本自身, 但两者都要实测, 不能靠推理定案.**

### ⚠ QR后必须合并材质, 否则红眼窝
QR的UseMaterialIds**会保留材质分区**到输出. 红色引导材质(0.8/0.15/0.15)随低模流到03/04, 04_bake只替换槽0 → 眼窝面(material_index=1)仍挂红槽 → 渲染/烘焙产物眼窝发红.
隐蔽处: diffuse**贴图**是对的(饱和红像素0, 因烘焙采样原版高模肤色贴图), 红的是**网格材质槽**. 只查贴图会漏判, 必须查网格槽数.
修复: 02_qr_auto步骤8.5, 布线完成后立即丢弃引导材质(Blender 5.1: `materials.pop()` 不再接受 update_data 参数; 先 foreach_set material_index=0 再 while len>1 逐个 pop).

### ⚠ 引导材质必须存独立文件, 不能改烘焙源
`01_1_eye_socket.blend`同时是04烘焙的高模源(烘焙遍历所有材质的贴图节点). 在它上面加红材质→眼窝烘红. 所以输出`_qr.blend`: 02读_qr版, 04仍读原版.

**实现**: 见1b — 赋材质判据(3D距离, 不是XZ投影)、QR后合并材质、引导材质存独立文件三条都在那里, 此处不重复。

补充教训: ①**引导用的辅助材质/属性用完必须清**(同rim倒角权重/bevel属性); ②烘焙产物自查要同时看**贴图像素**和**网格材质槽**, 两者可能只错一个; ③判"红"按目标色饱和特征(R>0.6且G,B<0.25), 不能用R>G>B(肤色本就如此, 会把正常贴图全判红).

**Blender 5.1 API**: `mesh.use_auto_smooth`/`auto_smooth_angle`**已移除**, 法向分割正解是`mesh.set_sharp_from_angle(angle=rad)`+全面`polygon.use_smooth=True`+FBX导出`mesh_smooth_type='EDGE'`(合法enum只有OFF/FACE/EDGE/SMOOTH_GROUP, 写FACE_EDGE报错). 本轮最终没用上法向分割(材质方案更优), API留档.

## 2. rim倒角选边: 最近边法 + 切向过滤, 两个条件缺一不可

给特征轮廓(rim)附近的边赋倒角权重时, 两种失败模式都实测踩过:

**失败模式A — 带宽法**: "边中点距轮廓<Nmm带宽"选边。QR低模边长中位与带宽同量级时, 带宽抓到2~3排交错碎边(实测138条散布0.56~3.0mm), 特征周围的碎线全带上倒角权重。

**失败模式B — 只查距离的最近边法**: 对轮廓每点取点-线段距离最近的边, 距离阈值再紧也不够。retopo网格的布线不与特征轮廓对齐, 很多轮廓点的"最近边"是**横穿轮廓的斜边**(实测25条里14条切向角44~77°), 用户在GUI里一眼认出这些碎线带权重。

**正确(已验证)**: 距离+方向双条件:
1. 对轮廓每个点, 取点-线段距离最近的边, 距离阈值自适应(0.4×局部边长中位, 下限1mm)
2. **切向过滤**: 边方向与最近轮廓段切向的夹角<35°才保留(用|dot|取锐角), 横穿边直接拒掉

效果: 138条(带宽)→25条(只距离)→14条(距离+切向), 剩余全部顺着轮廓(切向角<32°, 距轮廓<1mm), 斜跨碎边=0。验证脚本要逐边打印(长度/中点距轮廓/切向角/分类)并统计斜跨数, 不能只报总数。

**最终结局(2026-09-08 A方案): 即使做到14条全贴轮廓, 用户GUI复核仍判定"明显没有任何存在的必要"→整套机制删除**。原因: 这14条仍是不成圈的散短线段(6段), 因为上游rim预锐化失效导致QR根本没有rim边环(见第4节bug), 倒角落在碎边上既不连续也无实际锐化效果, 只剩视觉噪声。删除范围: rim_pre_sharpen.py+rim_bevel.py两脚本、01a的rim锐化步骤、02直接用眼窝高模、03更名并主动剥离bevel属性。眼睑缘锐利度改由烘焙法线贴图从高模获取。

**前置判据(下次直接跳过整套弯路)**: 做"沿特征线加倒角权重"前, 先验证特征边环是否存在 — 对轮廓每点找最近边, 检查连通分量是否≈2个闭合环(L/R眼各一)。无环时任何选边法都只能抓到碎片, 不如不做。在已有产物上删bevel属性是安全的: `attributes.remove`不动几何(顶点位置0位移), 骨架/连接/动画全保留。

通用规则: **凡按"距某曲线/轮廓近"选网格边做特征操作(倒角/折痕/缝合/seam), 必须同时校验边方向与曲线切向的夹角** — 近不等于顺着, 斜跨边在密集网格上必然大量出现。

## 3. FBX导入残留微旋转

xremesh输出FBX经Blender导入后对象带 -1.629e-7 rad (-0.000009°) X轴旋转(FBX轴向转换的浮点残差), 会被下游产物一路继承。导入后立即 `transform_apply(location=False, rotation=True, scale=False)` 归零(顶点位移~0.3微米可忽略)。

## 4. bmesh写mesh属性顺序bug

先 `me.attributes` 写值再 `bm.to_mesh(me)` 会把属性**整个冲掉**(to_mesh重建几何数据层)。正确顺序: bm.to_mesh(me) → 再写attributes → me.update()。此bug曾让高模rim预锐化静默失效(修改器挂着但无权重属性, BEVEL无效果)。

## 4b. 眼睑缘打点模板: 解剖驱动分段采样, 不是等弧长采样

**旧版缺陷(等弧长采样)**: 沿整条闭合轮廓等弧长取12点, 三个实测后果:
1. **没有一点真正落在眼角上** — 眼角位置由弧长决定, 不受控
2. **名字与实际位置相反**: "01外眼角"实测x=19.6mm(内侧), "07内眼角"实测x=43.7mm(外侧)
3. 名义"上睑5+下睑5+眼角2", 实际变成"上睑6+下睑6", 分界不在眼角
根因: 源轮廓(3DDFA)每眼只有6个点, 等弧长插值不保证特征点落在解剖位置。

**正确做法(解剖驱动分段)**:
1. 内外眼角 = 轮廓**x极值**(|x|大=外眼角, |x|小=内眼角) — 解剖事实, 不靠弧长
2. 以两眼角为界拆闭合轮廓为两段弧, **长弧=上睑**(实测R上睑40.25mm/下睑38.30mm)
3. 上下睑各自等弧长取**内部**点(端点就是眼角, 不重复放) → N点+N点严格对称
4. 下睑弧也是从外眼角走到内眼角, 但闭合顺序要求"内→外", **必须反转**([::-1])

**可视化与防误选**(用户提的三个痛点):
- 配色分组: 眼角=黄+尺寸1.5×, 上睑=青, 下睑=橙; 存自定义属性`lid_group`/`order_index`
- 顺序线: 闭合样条穿过全部点 + **驱动器**(不是Hook)绑定点位location → 拖点实时跟随。
  驱动器是纯数据API不需编辑模式选区/上下文, Hook需要(`vertex_indices_set`赋值很脆)。
  曲线对象放**独立集合LM_VIS**, 绝不进LM_R/LM_L — 下游按集合遍历会把曲线当标记点(location=(0,0,0)把轮廓拉向原点), read脚本也要加`if o.type=='EMPTY'`过滤
- 防误选: 原始模型`hide_select=True` + `lock_location/rotation/scale=True` — 视口可见可看纹理但点不中
- 模板源优先读用户手调轮廓(保人工成果+分辨率高), 回退3DDFA原始
- Blender 5.1 曲线样条类型enum是**'POLY'**不是'POLYLINE'
- 驱动器transform_type enum是**'LOC_X'/'LOC_Y'/'LOC_Z'**不是裸'X'

## 5. 测试管线时保护用户手调数据

read_eyelid_markers.py 会重新生成 eyelid_contour_manual.json(用户手动微调的眼裂轮廓)。headless跑测试链(place→mirror→read)会把它覆盖成自动点位数据。规则:
- 测试前 git status 确认手调文件干净
- 测试后必须 git checkout 恢复手调json
- 下游依赖它的脚本(rim_bevel选边)在恢复后必须重跑
- 例外: 用户自己在GUI里重跑管线并手调过点位后, git diff里的手调json是**用户新成果**, 要随修复一起提交, 不能checkout回旧版

**归属判定(动手恢复前必做)**: 文件mtime与某个管线log的mtime**精确到秒相同** + 该log对应脚本里有 `json.dump(...open(OUT,"w"))` → 是管线自己写的, 再对时间线判断是用户跑的还是我跑的。别一看到diff就假定是自己污染。

**坐标数组diff行数巨大 ≠ 数据丢失**: 442行全变可能只是**起始索引旋转**(同一组点换了起点)。判定法: ①`np.sort(点集,axis=0)` 后逐点比对最大差(≈0=同一组点); ②新起点在旧数组里的最近点索引(=旋转量); ③周长/宽高比/中心等几何特征是否一致。逐点位移会因顺序错位而虚高, 不能当判据。

## 6. 用户GUI复核是交付关口

数值自查(计数/距离/对称)全过≠用户满意: 选边类修改用户在Blender GUI里选中边看权重面板, 一眼能认出"不该有权重的碎线"。凡改动边级属性(倒角权重/折痕/seam), 交付前除数值自查外, 主动用逐边明细表(位置/角度/分类)自证, 并预期用户会GUI复核一轮; 被指出问题后先跑逐边诊断脚本定位性质(贴轮廓还是斜跨), 不要猜。

### ⚠ 几何对称性/范围类结论必须定量算, 不能采信渲染判读
渲染图判读在这类问题上系统性误报, 实测三类假阳性:
- **"左右不对称"** ← 低模quad布局两侧不同, 面数不等(79 vs 100)但**面积**只差3.5%。要比面积, 不比面数。
- **"爬到了额头/超出轮廓"** ← 要算**带符号**的超出量(特征z最大值 − 参考轮廓z最大值), 负值=未超出。视觉上看到色块大就断言越界, 会错。
- **"边界没沿轮廓走"** ← 材质/seam边界在低模上**只能沿边走**, 锯齿是固有形态不是缺陷。要量的是边界到轮廓的最近距离中位数(mm级)。

定性判读只用于"有/无、穿帮/不穿帮", 且要等贴图渲染完成后才问; 凡涉及数值(对称、范围、距离、面积)一律自己算。

## 7. 上游重拓扑后, 手调EMPTY标记点是否仍有效

绑定类打点(ARP关节点等)是EMPTY的**世界坐标**, 不依附网格顶点 → 上游QR重跑后(布线变了但同一角色)点位通常仍有效, 不必让用户重调。用只读脚本判定, 两条都过就可沿用:
1. **bbox三轴尺寸相对差 <0.01%** → 同一几何, 仅布线不同
2. 旧网格随机采样2万点 → 新网格KDTree最近距离: **中位~1.4mm / max~4mm 属正常**(QR重新布线的表面偏移)。判据别设太紧 — <0.5mm会把正常重拓扑误报成不同代际

然后只重跑打点**之后**的步骤, 跳过打点步。

⚠ 仍**绝不headless重跑打点步**: 它会覆盖用户手调的blend(只留一份备份)。要么让用户在GUI里自己跑, 要么写移植脚本把手调EMPTY搬进含新网格的文件。

## 9. "UV乱掉/纹理全乱"先查贴图代际错配, 不是UV数据

用户报"05输出模型UV乱了, 打开纹理显示身体上的纹理全乱". 实测根因**不是UV坏**:
- UV层都在、活动层都是UVMap、范围合法; UV数据03→04逐loop差**0.000000**
- 真因: 05全系列产物是**旧网格代际**(144,607顶点/144,648面), 而磁盘`04_diffuse_4k.png`是后来用**新网格**(144,373)重烘覆盖的; 05的贴图是**外链**(packed=False)指向该png → **旧UV配新贴图 = 纹理全乱**

排查法: 逐环节打印 顶点数/面数(判代际) + UV层名/loops/UV范围 + 每个image的`packed_file`与`bpy.path.abspath(filepath_raw)`及其mtime. 代际不一致 + 外链png的mtime晚于产物 = 错配.
修复: 从改动那一步起**重跑整条下游链**统一到新代际, 使贴图与网格同代. 修后全链6文件同代际, UV逐环节差0.000000, png(烘焙时刻)被下游产物正确引用.
⚠视觉终验要渲染**带贴图**成品(EEVEE, Blender 5.1引擎名是`BLENDER_EEVEE`不是`BLENDER_EEVEE_NEXT`): 身体/面部纹理连续、衣服对位、眼球有瞳孔虹膜不发红. 只查UV数值不够(本例UV数值本来就没错).
⚠重跑05链时**绝不headless跑step1打点**(会覆盖用户手调17关节点位) → 见第7节, 用移植脚本把手调EMPTY世界坐标搬进step1新产物, 跳过GUI手调(点位是EMPTY世界坐标不依附网格顶点, 上游换代后仍有效). 实测移植17/17, 世界坐标与手调源偏差<0.05mm.

## 8. 长Blender任务的执行方式

在 `execute_code` 里 `sleep` 轮询长任务会撞**5分钟内核上限**, 内核被杀会**连带杀死Blender子进程** — 日志停在半路, 白跑一轮。正确做法:
- **terminal 前台 + 宽timeout**: 命令一完成即刻返回, 不会白等, 是长任务首选
- 或 `background=true` + notify
- 必须轮询时, 循环总时长压在4分钟以内

⚠ 内核被杀后先查 `tasklist` 确认进程是否还在、日志是否有完成标记, 再决定重跑 — 别假定它跑完了, 也别假定它没跑完。
