- 动手前先搜一遍既有约定: 同管线脚本注释里常已写明方针(`02_qr_auto.py` 顶部原文: "测试阶段产物权威位置是 02QR拓扑/输出, 不是交付/") —— 搜到就按它做, 不要自创。
- **备份统一放项目根 `_备份/`(按原路径镜像), 绝不堆在输出目录里**。输出目录只留当次活文件, 一个东西一个**规范名**(如 `01_1_eye_socket.blend`); 要留的旧版改名后进 `_备份/`。理由: 用户在终端里会 clean 输出目录, 堆在那里的备份是纯噪音; 而 `.blend` 被 `.gitignore` 排除(单个 60~80MB), 做法/参数/判据在 git + `logs/*.md` + skill 里都有, 文件快照**只**用于几何 A/B 对比。`.blend1`(Blender 自动备份)也定期一并收进 `_备份/`, 并在 `_备份/README.md` 写明"可随时整体删除"。
- 覆盖任何文件前(含用户放在工作目录里的)要留快照, 但放进 `_备份/`; 名字带**权威**的文件(`01_AI打点_手调权威备份.blend` 等)任何情况都不动。
- 用户的手描/标记数据(`eyelid_contour_manual.json`、`01A_markers_eyelid.blend` 等)是**他的资产**, 不只读取, 也不要挪位置/改名 — 要改先问。

## 2. 存盘前切回 OBJECT 模式
管线脚本常停在 edit 态就 `save_as_mainfile` → 文件存成编辑态, 用户一打开就在编辑模式(容易误改)。
存盘前 `bpy.ops.object.mode_set(mode='OBJECT')` + `select_set(False)`, 并核对一次 `o.mode`。

## 3. 诊断/量测脚本的坑
- **日志可能是上一轮的**: 脚本崩了(如 `Vector - ndarray` 类型错)就不会重写日志文件, 你读到的还是上次数据, 会据此得出错误结论。读前确认日志刚被重写(mtime / 末尾 DONE 标记), 并且脚本不要在异常后静默结束。
- **产物路径一改, 所有诊断/渲染脚本里硬编码的旧路径一起改**: 否则它们静默读上一版文件, 给你一份"毫无变化"的旧数字(据此误判过一次)。改路径时把项目里全部 `_*.py` 一起 grep。**生产脚本的读入也要同样全量 grep** —— 实测把产物搬到新位置后, 赋材质/眼球摆入/眼窝开孔 3 处生产脚本仍在读旧位置, 是端到端测试才暴露的; 改完路径必空跑一次全链(§6)。改路径的稳妥做法 = **断言式替换表**(每处替换 assert 命中才写盘)+ 全项目路径存在性核对 + 跑一个真实 stage 当冒烟 —— 实测数十处替换零失配、02 全链分钟级通过即可收工。
- **环/边界追踪过度数 >2 的岔口要"直行优先"**(选与入射方向最接近的邻边), 否则会拐到同一网格上别的开放边界, 量出十万顶点的假环、渲染也乱。
- 度量结论要用同一套判据对比旧版(基线对比), 并在报告里给中位数 + p90 + max, 单看均值会漏掉尖刺/离群点。
- **批量改文件: 编辑脚本先 `write_file` 落盘再执行, 不要用终端 heredoc 内联** —— heredoc 里生成的 python 字符串中的 `\n` 会被再解析一次变成真实换行, 写出的 .py 直接语法错误(同一坑一轮内踩了两次); 命令文本里出现 `&`(如集合交集 `a & b`)还会触发终端工具的后台化守卫误判。两者都用"脚本落盘 + 跑脚本"绕过; 落盘脚本照旧放 `logs/_*.py` 并在写盘后 `ast.parse` 自检(断言式替换表见上一条)。
- **命令行传参/判失败两坑**(各实测踩过一次): ①bash 参数对拼接别用 `:` 当分隔符 —— `${pair%%:*}` 会被 Windows 盘符(`E:/...`)的冒号从头部截断成 `"E"`, 分隔符选值中不会出现的字符(如 `|`)或直接写显式数组; ②`cmd | grep … || echo FAIL` 的失败传播绑在 grep/head 上(head 成功就永远不报 FAIL) —— 判失败要么取原命令退出码, 要么先落盘日志再单独 grep。
- **交给原生程序(Blender/xremesh 等 exe)的输入输出路径一律写绝对路径**: 原生进程的 CWD 与 shell 的 `cd` 不一定一致 —— 实测相对路径被 Blender 解析到 `C:\` 而非项目目录, 渲染/保存静默写到意外位置(用 `find` 全场找图才发现)。

## 4. 汇报纪律
- 被问"现在没问题了吗": **如实列出未解决项与已知风险**, 不把未定稿的阶段说成完成。
- 用户说"这个是最新的吗 / 感觉没啥区别"时, **先确认他打开的是哪个文件**, 再解释差别在哪。三个指纹区分同名/近名 blend:
  材质槽列表(出现 `EyeSocket` = 还带材质分区/碗的旧版)、**开放边**(数正好等于两环顶点数 = 已掏空的"环+空腔"版)、
  对象模式(OBJECT vs EDIT)。截图里能看到红色材质 + 眼窝被填满 ⇒ 他看的是旧版, 不是刚交付的掏空版 — 直接指出来, 别重做。
- 亚毫米级改善(环抖动 0.27→0.13mm 这类)**正常缩放下就是看不出来**: 主动说明量级、并指出"这一轮肉眼可见的变化是 X"
  (如"环内从填满变掏空"), 不要靠再渲一张图硬凑差异。
  **宣布任何"优化了"之前先做可见性自检**: 位移/曲率变化 ÷ 结构尺度(眼宽 ~35mm) —— ≤~1% 量级直接说"肉眼不可见";
  把不可见量级的上限(如 0.33mm 的软化)当成果汇报, 用户就会回"依然没区别"。
- 用户回"依然没区别 / 你都改了啥"时, 正确回应 = **逐版本对账表**(版本 | 改了什么 | 实际位移 | 是否可见),
  先摆量级再谈机制; 查出"从未执行"或"不可见"的版本直接承认, 不要堆解释 —— 对账表常能暴露真正的 bug(如静默未执行的 pass)。
- 用户截图报"这里不对"时**先确认是哪只眼/哪个部位再动手**(左右眼在同一张脸上, 症状往往不同): 先说出你判断的部位让他确认,
  或按图里的可见特征(材质/是否有洞/线框密度)判定。部位认错会把整轮诊断与修复都做在另一只眼上。
- 每个阶段改完先给用户可检查的中间件(带渲染图 + 路径), 停等确认再跑下一级; 不要在未验收时一路往下推。
- **平滑类指标变好 ≠ 形状对**(同一个坑踩过两次): 每改一版必须同时给 ①形状类硬指标(如洞口轮廓到手描线的 XZ 偏差、被改表面的最大位移) ②同一机位的前后对比图(正视图 + 俯视图 + 用户关心的那个角度)。只报转角/抖动这类指标, 会把"轮廓被拽进 1.5mm""整圈表面被改 1.6mm"这种改坏当成成功交付。
- 各 stage `输出/` 只放当次活产物; 未定稿/旧版进项目根 `_备份/`(现无交付目录)。
- **同一条修复路线失败两次就停手换法, 不要连试变体**: 先把工作文件从 `_备份/` 拷回上一版好的状态,
  再把"每条路的实测代价 + 推荐哪条 + 需要他定什么"一次性摆给用户。几何手术/重建类修改每轮都会引出新副作用
  (实测同一条边界重建路线迭代十余轮: 拆长边→引长边→撕开边界→圆盘越修越大), 而最终判断权在用户眼睛上;
  连试下去只会把工作文件留在半坏状态。
- 报告结尾必须写清"**这一版还剩什么没解决 + 被哪条安全闸挡住 + 下一步的代价**", 而不是只报本轮进展;
  用户据此决定继续还是收手。

## 5. 系统重启/崩溃后的完整性核查(几分钟, 先做再继续)
用户机器可能被 Windows 更新等自动重启中断, 恢复会话后按序核查(全部只读):
1. **中断点**: `cat /proc/uptime`(git-bash) 得开机时长, 与 `date` 相减得重启时刻;
   再看重启时刻之后有没有文件被写(`find . -newermt "<上次停工时刻>" ! -path "./.git/*" ! -name "*.png" -type f`)
   —— 空输出 = 重启没打断任何写入。
2. **半截保存**: 扫 `*.blend@`(Blender 写一半的残留) —— 有则对应文件不可信, 用 `_备份/` 上一版重做。
3. **产物完整性**: 不要只看文件大小 —— **headless 打开每个关键 .blend**, 数对象/顶点/面 + 用 `mesh_health_check.py`
   核眼环闭环; 全过才算无损。
4. **git**: `git status -sb` 确认与 origin 同步(有未推提交补推); 手调资产(手描 json / 标记 blend)按 mtime 确认未被动。
5. **定时任务**: 有 cron 的确认有没有该跑没跑的。

## 6. 全流程连跑测试(改动过管线脚本后必做)
- 顺序: 01修复 → 01a眼窝 → 02(**QR → 碗 → 眼球摆入并并入**) → 03UV → 04烘焙 → 05绑定(无头可全链跑: `printf '05\nquit\n' | DEMO_SKIP_GUI=1 python 控制台.py`, 实测 ~1.5min; 打点半自动在无头下走算法默认点, 用户真实运行仍是 GUI 微调)。
- **眼球在碗之后摆入、并入正典输出**(2026-09-17 用户定; 碗=纯 rim 几何, 碗脚本里不许出现任何眼球依赖 —— 曾残留"缺 01_2 就跳过"把整只眼跳过; 摆入后由 `run_eyeball_v2.py` 末尾幂等并入 `02_qr_150k_socket.blend`): 01a 只做眼窝(工作输出仅 01_1); 02 = QR → 碗(深度/环数由 rim 几何自算) → 眼球摆入。眼球**自 02 输出起全程携带**: 03 不动眼球自带 UV(`map1`); 04 的**对象选取禁用 `[0]`/索引取物 —— 一律显式名或"顶点数最大"**(多一个球会静默选错; 高模从"新载入集合"里取最大); 04 的 FBX 导出选择**所有剩余网格**(含眼球), 不是只选低模。05 仅在网格缺眼球时才从 `01a眼窝眼球/输出/01_2_eyeball_placed.blend` 并入(已有则直接用, 免得出现两对眼); 蒙皮(顶点组权重 1 + Armature 修改器)写在 if/elif 之外两路共用 —— **顶点组名必须用骨架实取骨名(去前缀同义匹配), 不得硬编码 `mixamorig:Head`**: retarget 前骨名无前缀, 硬编码会让眼球在 03/03B 静默不动(实时变形失效; LBS 数学自查全绿也照样不动), retarget 加前缀后才碰巧对上。验收 = 活体探针(转 Head 骨 10° 测顶点位移, 0.00mm=名字没对上), 细则与探针脚本: `references/skin-binding-name-sync.md`。**眼球必须在 05_3B 重摆之前完成蒙皮** —— 3B 的 LBS 只处理"有顶点组+修改器"的网格, 否则眼球原地不动、与重摆后网格错位(细则与残留: `eye-socket-boolean-cut.md` §眼球生命周期)。
- 跑前: 手调资产 + 当次产物备份到 `_备份/<日期>_全流程测试前/`(原路径镜像); 跑后 `git status` 复查。
- **04 的"烘焙后贴图溢出处理"是自动步骤**(`04纹理烘焙/scripts/texture_fix.py`, 由 `04_bake.py` 在 Diffuse 保存后调用并 `img.reload()`, 让 blend/FBX(embed) 携带修好的贴图)。**一次性修复必须自动化进管线** —— 只留"某次手工修好的产物文件 + if-exists 挂钩"的修复会在 clean/纯净重跑后无声丢失、问题整体回归(贴图溢出整轮复现)。判据与三个坑(皮肤占比/窗口多数类判据会把真渗出全漏掉; 必须整块排除衣物连通块, 否则衣物边缘被吃成毛边; 复算残留要同口径重算衣物块)见 `blender-uv-texture-baking` → `references/ai-texture-color-bleed-fix.md`。
- 每阶段独立日志; 判成败**必须 grep stdout 的预期成功打印**(blender 脚本异常时退出码仍为 0, 见 `eye-socket-boolean-cut.md` §静默失败陷阱); 失败即停并记录停在哪一步。
- 基准用时(实测, 16 万面级低模链): 01修复 ~4min / 01a 眼窝 ~2min / 02(QR+碗+眼球) ~2.3min / 03UV 秒级 / 04烘焙 ~0.5min / 05绑定 ~1.5min。远超基准 = 卡死信号(QR 引擎完成为 `progress.txt==2`)。
- **三角面预算(用户已定, 别再建议改)**: 核查上限 = **35 万 tris**(阈值 350,000; 该检查只是提示、不阻断); QR 目标保持 **150k 四边面**(实测三角化 ~32.2 万, 在限内)。此前"把目标改到 140k"的建议已被用户否决。
- **核查输出别被措辞骗**: 眼洞的**边界边/开放边是正常态**(数量 = 各孔环顶点数之和), "非流形"看的是 **>2 面共边**; 脚本把边界边打印成 "Non-manifold" 会让人把正常态当回归(实测虚惊一轮)。体检输出把"边界边"与"非流形边"分别命名、分别打印。
- 链内读入是要长期维护的: 03 读**带碗版** `02QR拓扑/输出/02_qr_150k_socket.blend`(不是裸 QR 输出); 04 的高模读 `01a眼窝眼球/输出/01_1_eye_socket.blend`; 02 读 `01a眼窝眼球/_中间/01_1_eye_socket_qr.blend`。改完空跑全链验证"零手动交接"。
- **重跑子链前先查每个脚本的真实 IN**: 链里存在"模型入口中间件" —— 05 的 step3 读 `02_go_detect骨架.blend`(由 step1 从 04_bake 生成 + step2 go_detect 产出), **不是**直接读最新 04。跳过 ①② 只重跑 ③④ 时, 下游全程带着中间件里的**旧模型数据**(实测: 眼珠重摆后 03~06 仍带旧位置, 排查两轮才发现是它在作怪)。修正 = 外科式同步中间件里变化的那部分(如只改眼珠对象位置),
  **不碰手调文件 `01_AI打点.blend`** —— step1 重跑会"备份后覆盖"手调标记, 属禁止路径; 跳步重跑后的产物只作当下核验用, 全链一致性以用户的完整重跑为准。
- **QR 与 01a rim 带重建有 run-to-run 波动**(同脚本同输入两次跑出的角部干净度可有差异): 已验证好的产物先备份再重跑; 重跑变差就回退备份 —— 不要假定重跑得到同样结果。
- **无头端到端测试法**: `printf '01\n01a\n02\n03\n04\nquit\n' | DEMO_SKIP_GUI=1 python 控制台.py` —— 直接测的就是用户入口; 不设 `DEMO_SKIP_GUI` 时打点类 GUI 步骤会停下等输入。每阶段细节日志在 `logs/<tag>.txt`(如 `02_QR.txt`/`02_碗.txt`), 成败看该文件的成功打印, 不看退出码。

## 7. 周期性清理(用户会点名要求)
- 对象: 工作区根一次性脚本 `_*.py`(会积到上百个)、`*.blend1` 自动备份(可到数百 MB)、`logs/` 历史渲图(可涨到 GB 级)、`__pycache__`。
- **先列保留清单再删**, 至少含: ①生产脚本的运行读入(链内读入见 §6; 旧碗参考件 `_eye_cup_ref.blend` 已不是任何脚本的运行读入, 可删可留) ②`_备份/` ③进度/结论 md ④当轮验证渲图。删错运行依赖 = 直接断链。
- `logs/` 用 mtime 只删旧一轮(如 `find logs -type f \( -name "*.png" -o -name "*.jpg" \) -mmin +90 -delete`), `*.md` 与当次测试日志保留。
- 删除清单落盘 `_备份/<日期>_清理清单.txt`; 被删文件若有 git 跟踪, 提交并说明, 不要留一堆 `D` 悬在 status 里。
- **用户要跑终端 clean all(清空输出)之前**: 先确认 ①`git status` 全部提交(重要东西不能只在工作区) ②手调资产(手描 json、标记 blend、手调点位)已有 `_备份/手调文件_权威/` 副本 —— clean all 会删输出目录, 被删的运行读入 = 直接断链。
- **终端 `clean` 的语义**(控制台.py, 用户会实测; **改完必须自己实跑验收** —— 曾被路径改造误删核心逻辑, 变成只扫 `.blend1` 的空壳且 `n` 未初始化, 到用户真要用时才暴露)。
  - ①各 stage `输出/` **递归**清空; **清空后连空目录本体一起 `rmdir`** —— 用户直接在文件管理器里看目录树, 空壳文件夹(`screenshots/`、`_中间/`)也算"clean 不掉"; 含手调文件的目录不会空、自动保留。②各 stage `_中间/` 一并清(不删 = 下游读到旧产物, status 误报"已生成"); `screenshots/`、`__pycache__` 一起收。
  - ③备份类扫描(`*.blend1`、`01A_markers_eyelid_备份_*.blend`)必须**递归 `**/`**: 备份会躺在子目录(如 `输出/`)里, 单层 glob 静默漏掉(实测 80MB 备份残留、被用户点名)。同类规范: 要删的文件类别必须在**同一处删除逻辑闭环**, 不许"A 处跳过、靠 B 处扫描兜底"。
  - ④**删除失败必须醒目上报**(失败清单 + 提示"多半被 Blender 占用, 关掉后重跑"): `except: pass` 会把失败伪装成"clean 不掉"。
  - ⑤clean 会删掉清空后的 `输出/` 目录本体 → **python 写手写前必须 `makedirs(dirname, exist_ok=True)`**(Blender `save_as_mainfile` 会自动建目录, `shutil.copy2` 不会)。
  - **绝不删**: 脚本/手调 json(3ddfa 轮廓/虹膜)/手调点位备份/原始文件/`_备份/`。
  - **`01a眼窝眼球/输出/01A_markers_eyelid.blend` 属于"可清"**: 它是用户跑 01a GUI 即可再生的标记工作文件, 权威副本在 `_备份/手调文件_权威/01A/` —— 别把它列进 PROTECT 清单(曾因列入保护被用户点名"clean 不掉"), 也别与 `3ddfa/*.json` 手调数据混为一类。保护清单只收"不可再生"的数据。
- **"深度整理"= 全层扫描 + 逐件 grep 引用后才动, 移动不删除**(用户会在文件管理器里点名追问每个可疑文件; 只查正在做的那层会被当场抓出"你真的都仔细查了吗"):
  候选清单必须覆盖 ①工作区根散件(`_*.py` 补丁脚本、参考件 blend) ②各 stage 根 ③交付镜像目录 ④空壳目录;
  每件先在全生产脚本里 `grep -rln <名字>` 确认零引用, 并核它自己引用的文件是否存在(引用缺失资产的 = 死脚本, 一并归档);
  归档进 `_备份/<主题>_<日期>/` 并写归档 README 逐件说明用途(保留 = 决策过程证据); 空壳目录连本体删;
  git 跟踪的散件移动后用 `git add -A` 让 git 识别 rename(不删不悬); 收尾跑 `printf 'status\nquit\n' | python 控制台.py` 核 11 项全 ●。

## 10. 参数纪律: 禁止死参数(用户会点名复查)
用户会直接追「再检查是不是死参数」(换原始模型的可能性一直存在)。新增的每个数字必须归入三类之一: ①模型实测推导(如带宽=系数×实测眼宽、均距=周长/K、窗口=名义值倍数) ②无量纲比值(阶梯/限幅/早停相对参考带、面形判据角度与长宽比) ③策略预算(迭代次数、核权重、轮数上限 —— 最终由实测择优兜底)。绝对毫米的窗口/半径/阈值一律改为随推导量缩放; 交付修复前自审一遍并能逐条给出推导来源; 审计后复跑核实行为未变(选定参数/指标一致)。完整审计流程与实例: `references/rim-band-qa.md` §5。
