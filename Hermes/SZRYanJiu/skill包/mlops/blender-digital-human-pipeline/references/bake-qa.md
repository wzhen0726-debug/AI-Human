# 烘焙审核机制（04阶段, bake_qa.py）

## 为什么要它
04烘焙的脏块/拉伸**多半不是烘焙阶段的错**——先查上游UV。本项目实例: 03择优缺陷选中密度比1.81的坏UV(CV 0.215 vs 基准0.119), 烘焙在密度两倍不均的UV上必出脏块。烘焙代码没变、只有UV变了 → 脏块出现。**先量UV密度CV(与03同口径), 再怀疑烘焙设置。**

## 三项指标(全部无量纲/自参照, 无绝对阈值)
- **未填充 unfilled**: 每面取中心(loop_start+loop_total//2)与首角两个UV采样点 → 查贴图 alpha<0.5(无alpha通道则判 RGB和<0.004 纯黑) → 占比。烘"空洞"直接度量。
- **脏块 dirty**: 8px块中位色 vs 3×3邻域中位(roll堆叠) → 偏差 > 全局MAD×6 的块占比(仅填充区)。衣物纹理细节抬底噪, 只用于轮次间相对比较, 不看绝对值。
- **密度CV**: 每面 uva/3D面积 的 std/中位, 与03同一口径。

## 轮次与择优(参数全活)
- 边距阶梯 = 既有基准(16px) × [1, 1.5, 0.6] —— 相对量;
- 每轮: bake → save临时件 → **同一套贴图处理(溢出+离群清理)** → 测量;
- 择优 = 字典序 (unfilled, dirty, cv) 最小 —— **不要加权求和(权重=死参数)**;
- 双零早停; 选定轮 copyfile 为正式文件; 临时件清理; 处理失败不阻断。

## 坑
1. **最终写回不能用 img.save()** —— img内存里是"最后一轮"的烘焙结果, save会把刚复制好的选定件覆盖掉。正确: `img.filepath_raw=最终路径; img.reload()`。
2. 测量用 `bpy.data.images.load(png, check_existing=False)` 后立刻 `np.array(img.pixels[:])` reshape(H,W,4); 用完 `bpy.data.images.remove(img)` 防泄漏。
3. UV 读取: `me.uv_layers.active.uv.foreach_get("vector", arr)`(5.x API; 旧写法 uv_layers.active.data[...].uv 逐条循环慢)。
4. 块统计先 trim 到 block 整数倍(`[:hb*block, :wb*block]`)避免 reshape 失败。
5. 轮次临时件要带轮号前缀(_qa_r1_diffuse.png), 避免与正式件/贴图处理备份混淆。

## 实测参考(2026-09-18, 150k网格 4K)
3轮 margin 16/24/10 → 未填充 0.07%/0.03%/0.12% → 选24px; 密度CV 0.112(=好UV); 单轮约1.5分钟(4K bake≈40s + 处理≈30s + 测量≈10s)。

## 边距↔清理半径必须同源(实测事故)
margin 16→24 后, 贴图溢出处理 `fix_diffuse_png(reach_px=18)` 的18px是按旧margin调过的 → 24px渗出带超出半径 → 衣物边缘残留深色环。修: `reach_px = 本轮margin + 4`(4px=过渡保护; 基数=实际烘焙设置)。**凡"按边距膨胀"的产物清理, 作用半径必须与边距同源, 改一个就同步另一个。**

## 贴图修复自身造成的斑块(实测事故, 必查)

**分阶段 diff 才能归因**: QA轮次的自动备份(_备份/<时间>_04diffuse_处理前|v2前/)留存同一轮的 raw→v1→v2a→v2b→final 快照 → 逐对 diff 即可确定"斑块是谁造的"(实测: v1 一次改49,642px=主要源; v2 次要)。

**平涂斑块度量**(独立判据): `内部std<1.2 且 邻域梯度(max_filter 11)>25 且被修改过` 的连通块计数。旧 v1 实测 33块/最大748px/色差101 → 用户可见。

**两条硬规则**(踩过的坑):
1. **禁止整片填同色** —— 皮肤明暗沿边界连续变化, 全局中位色必造平涂斑块。逐像素取就近真实颜色(EDT最近色) + 掩膜内 Jacobi 扩散(边界像素固定不动) → 边界连续无面片化。
2. **必须留边缘保护环** —— 距“衣物本体”≤2px 的像素是边界自身的抗锯齿边, 替换它=把边缘啃出米色锯齿缺口(渲染 A/B 实锤)。

**验证三件套**(互相独立, 优先于目视——成对读图会前后矛盾): ①平涂斑块像素数 ②渲染级 A/B 差异占比(同机位换贴图) ③边缘完整性: 衣物暗掩膜(lum<48) raw vs final 的像素差(实测 68.4万px 仅差1px = 边缘完好)。

## 贴图修复阈值与保护区的两个致命盲区(实测事故)

1. **阈值差一点=盲区外**: v1 溢出清理用 lum<95, 而残留暗线实测亮度≈97 → 关键缺陷从未被清。**上线前先量目标缺陷的实测分布再定阈值, 并留余量**(修法: 加一遍 lum_th=112 的弱渗清理)。
2. **保护区域禁用几何代理**: v2 用"身高80%以下才处理"保护头部 → z>1.457m 整块上胸/领口/肩颈/腋前全被保护 → 用户三个绿框全在保护区内，v2 从未处理过这些位置。**修法: 保护区域必须用与被保护对象直接相关的量** —— 五官球: 球心=双眼对象中点, 球外全部可清理。
3. **保护球半径必须实测覆盖完整特征区(二次事故)**: 曾取 R=1.6×双眼间距≈109mm, 但下巴/下颌距球心实测 115~130mm = **在球外** → 唇缝/胡青/下巴阴影仍暴露在 v2 的"非肤色暗异常即替换"判据下, 有被误抹风险(已改 2.2×间距≈150mm)。R 的定法 = 先量该特征系统到球心的**最远点**(头面部到底≈2×间距)再加余量; 同时核上界(到锁骨/上胸 ≥250mm, 放大后碰不到此前刚解禁的清理区)。**单球保护必须测最远点验证覆盖, 不能凭"大概"取个系数。**

## 归因链(顽固残留必用)
源\|原始\|修复 三重同机位对比 + 射线定位取UV:
- 高模源贴图(如 8K basecolor) + 原始烘焙快照(_qa_rN) + 修复后 → 同机位渲染对比;
- 从正面/上方打射线命中低模面→低模UV; 最近点→高模UV → 在贴图空间裁同一处;
- **能直接回答"是谁造的"**(本项目实测: 高模源干净、原始烘焙有明显暗线 → 烘焙引入, 不是源贴图问题)。

**用户指认"最近的修复引入了大面积问题"时, 三步定量再回复**(实测: "为啥修个眼窝会出这么多问题"):
1. 量每个最近修复的**实际 footprint**(被修改 texel/掩膜占总图比例) —— 实测眼窝修复 = 源贴图 0.29% + 输出端 0.11% 且全在眼窝内部, 物理上够不到脸;
2. 双 blend(raw|adjusted)或 raw|final 做**同机位渲染像素 diff** —— 实测脸部仅 682px=0.035%(>30 的 8px), 两版脸完全一致 = 修复没碰脸;
3. 查问题在**最早版本(raw/未调整)里是否已存在** —— 在 raw 里就有 = 长期状态, 不是本次引入。
**"发现时刻 ≠ 引入时刻"**: 上游缺陷(如眼窝黑块)修好后, 用户才第一次细看别的区域, 会把长期存在的问题记到最近一次改动头上 —— 用 footprint + A/B + 版本回查这套证据讲清时间线, 不要顺着"再修"一个不存在的新引入问题。

## 替换类清理必须排除衣物/毛发边缘(实测事故)

v2 网格引导替换把衣物边缘的面当"暗斑"→周围皮肤色中位写回整个UV三角形 → 渲染呈**浅粉/米白毛边**(实测 6,092px, 93% 来自此项)。
**修**: 簇自身 lum<55(衣物级深色)跳过; 簇邻域深色(lum<48)面占比≥25% 跳过; v1 同理加"7px窗深色≥50%不动"。

**分阶段快照增量归因**: 每个修复子步自动备份(_备份/<时间>_04diffuse_处理前|v2前) → 对缺陷掩膜逐段统计增量, 一秒定位是谁造的(本项目实测: v1+425px / v2a+2883 / v2b+2784)。

## 双blend输出(04阶段, 用户要求)

`04_bake_未调整.blend`(纯烘焙) + `04_bake.blend`(烘焙+调整, 管线默认), 贴图同样两份 → 用户/自己都能一步定位"哪一步出问题"。实现: 每轮先存 `_qa_rN_diffuse_raw.png`; 选定后并出两份; 末尾 save_as_mainfile(copy=True) 各存一份。

## 交付blend的材质必须接上全部烘焙通道——法线!(实测事故)

**征兆**: 用户报"五官/皮肤全糊、无毛孔皱纹、发丝成色块"; 排纹理、排UV、排眼球都正常, 渲染怎么查都是"平脸"。
**机制**: 烘焙脚本烘 Normal 时会临时把 bake 目标节点接到 BSDF, 烘完为"避免影响FBX导出"又断开 —— **导出后从未接回**, 保存的 blend 材质只剩 BaseColor → 产物与所有QA渲染(含用户视口)都是"无法线平脸", 微观细节全丢。
**规则**: 凡为导出临时断开的材质节点, 必须在导出调用完成后、保存交付blend之前**原样接回**(法线=Non-Color 色彩空间 + NormalMap 节点)。"断开"只许存在于导出前后几行, 不许进入产物; 修复后重出文件(时间戳纪律) + 同机位 before/after 对照。
**复查(不靠肉眼)**: 打开保存后的 blend, 程序化打印 BSDF 的 Base Color / Normal / Roughness 各输入有无连线(及贴图 colorspace); 缺链先补线再重渲。
**修复效果先量再报**: 接通后做同文件单变量 A/B(只断/接这一项变, 同机位同光照) —— 实测观感差异**【很小】**。接上是产物卫生要求, 但**不得把它宣布为"五官糊"的主因**(主因通常是光照/视口, 见"视口观感 vs QA渲染"节); 未量化的因果断言=用户验证一次即被打回。

## 验证纪律: 渲染带纹理模型, 不只看贴图文件

多视角(整体+衣边特写×4~6), 且做**三维对照**(高模源|原始烘焙|修复后 → 与源的平均色差谁更小)。实测教训: 单看贴图文件无法发现渲染级现象(毛边/磨皮感), 且读图工具会夸大; 用与源色差定量校准(0.05/255的差异=可忽略)。
## S2A 烘焙的 cage/ray 必须按语义配对(实测事故)

**S2A 语义**: 射线从「低模表面 + 法线×cage_extrusion」出发、方向向内, 总长 = max_ray_distance。
- 旧配置 cage=bbox×0.011(≈20mm) + ray=bbox×0.056(≈101mm) = 笼20mm + 81mm乱跑 ✗ → 衣物/肩带覆盖处笼点高于衣物, 射线下降先打到衣物 → 皮肤 texel 被染衣物深色(渲染脏线, 射线定位实测) ✗。
- ray < cage 也不行: 射线够不到表面 → 大面积未填充黑斑(实测 8mm ray + 20mm cage = 全黑 ✗)。
- **正确配对**: cage 必须小于「皮肤到覆盖物间距」(定稿: bbox×0.0033≈6mm), ray = cage + 搜索余量 ≈ 4×低↔高实测最大偏差(定稿: +bbox×0.0044≈8mm)。先用 BVH 量低↔高的偏差分布再定值(实测本例最大仅 1.97mm)。
- 副效应: 小 cage 使未填充率上升(0.03%→0.38%), 由 margin 膨胀互补 —— QA 的「未填充」指标必须保留以监控。

## 被遮挡区域(眼窝内壁)必用隐藏遮挡物复核 + 双保险修复(实测事故)

**征兆**: 带眼珠看不到, 隐藏眼珠后眼窝内壁呈硬边黑色块; 带眼珠时在眼睑边缘/眼角露出。
**机制**: ①01a重建的socket内壁UV落在原贴图“眼球/睫毛”像素区 → 烘焙采回深色; ②低模内凹区法线平化 → 射线散打采到睫毛像素; ③部分texel未填充=纯黑。三者合成黑块。
**定位法**: 隐藏眼珠渲染→黑块像素→正交反投影→低模面/UV→反打高模→高模UV采样(看源像素是什么)。
**修复(双保险)**:
1. 源贴图: 眼窝内壁掩膜 → 周围皮肤填充 → 写成 `01_original_tex_fixed.png`(04的FIXED_TEX机制自动启用)。
2. 输出端: `04_bake.py` 每轮烘焙后对低模眼窝掩膜做EDT最近亮皮肤填充(皮肤源阈值 lum>105, 略偏亮防灰) —— 未调整/已调整两份都要过(该区=被遮挡内部, 统一按皮肤处理)。
**掩膜取法(实测定稿)**:
- **射线命中法 > 几何筛面法**: 从区域正前方布正交射线网格, 命中面(=透过开口实际可见的表面)光栅化其UV; 实测覆盖 3254 面, 而"面朝向+距离"几何筛面只捞到 852 面 —— 深部内壁漏掉, 修复怎么跑都盖不住目标texel。再叠"距(眼球)中心 ≤1.35×半径"距离门: 只留内部, 天然排除可见的睫毛/眼睑边缘(修复不得改写可见边缘内容)。
- **UV掩膜↔图像数组的行序必须统一**: UV空间 v=0在下, PIL/numpy 图像数组第0行在顶 —— UV空间生成的掩膜直接套到图像数组必须翻转(`mask[::-1]`)或统一按 (1-v) 建索引。方向错了=修复全填到上下镜像位置, 真区texel纹丝不动, 表现为"方法无效"的假象。
- **上线前用已知探测texel验证覆盖**: 修复前纯黑(0) → 修复后皮肤色才算成功; 不靠目视, 不靠"改动像素数>0"。
**自查证据图必须实际覆盖所声称区域**(踩过): 声称"看完整眼眶"的对照图, 裁切只到眉毛-上眼睑, 眼球区根本没进图, 被用户当场戳穿 —— 出图前先量目标区域在图中的像素范围, 再裁。
**教训**: 被遮挡区域必须隐藏遮挡物后单独自查; 内凹平化区一律按“内部皮肤化”处理, 不去与射线搏斗。

## "左右眼看起来不一致"先做数值对称核查再答复(实测)

用户或读图工具报"两只眼一个样"时, 先程序化排除真错误(数秒出数):
- 眼球顶点 PCA 主轴 = 角膜轴 → 对正前(-y)夹角; 左右镜像比较: **中心镜像偏差(mm) + 角膜轴镜像夹角(°)**;
- 两眼球 UV 是否镜像(按索引逐UV比"同向 vs u→1-u"最大差);
- 两材质参数与贴图逐项 diff(节点/连线/BSDF值)。
实测合格例: 中心镜像偏差 0.076mm、角膜轴镜像夹角 0.000°、材质完全一致 → 几何零问题; 此时视口"观感不一致"= 各自光照下的镜面高光差异(物理必然) + 虹膜图案不镜像(真人虹膜亦不对称, 自然)。**先排除真错误再答复, 不要为光照差异动模型。** 现成脚本: `scripts/eye_symmetry_probe.py -- <blend> [NamePattern]`, 镜像偏差/角膜轴/UV镜像/材质diff 四项一次输出。

## 中间态陷阱: 重跑期间输出目录的文件会短暂处于坏状态

重跑修复版时会先保存一版中间态(如密度未归一的坏UV) ✗ 若用户此时在自己GUI里打开/已经打开着该文件, **Blender不会自动重载** → 用户看到并报告的是旧中间态的缺陷 ✗(实测案例: 眼睛下眼睑深蓝黑月牙, 其实是中间态).
- 诊断法: 同机位渲染当前文件 vs 用户的截图; 同时检查同目录的 `.blend1`(上一版自动备份) —— 若 `.blend1` 复现用户症状而当前文件干净 → 结论=用户会话停了在中间态。
- 处理(交付闭环, 硬规则): **只让用户"重开窗口"不够** —— 用户以**产物文件修改时间戳**判定这轮修复有没有真干活; 反馈之后时间戳没变新, 会被直接质疑(实测被质问"你忽悠我是吧")。正确收尾: 用户反馈缺陷 → **立即重跑该环节, 让最终产物时间戳晚于反馈时间** → 附同机位渲染证据 → "重开/Revert"只作为补充提示(并警告别把旧会话另存覆盖)。
- 预防: 修复轮次的坏中间态不要占用最终产物文件名(坏状态存临时名, 或每轮跑完立即以完好版覆盖最终名); 发现自己上次留了坏保存, 先重跑再回复。

## 视口观感 vs QA渲染: 先复现用户视角, 再定性归因

**实测事实**: 同一文件、同一相机, 只换光照 —— 柔和环境光(≈ Blender 视口"材质预览"/studio HDRI): 皮肤平、软、细节被漫射光抹平; 方向光(太阳): 结构立体、五官清晰。观感差距大到用户怀疑是不是同一个模型/文件。
**触发场景**: 用户拿视口截图说"糊/五官不对/和你的图不一样/找不到这个模型"。
**答复流程(证据优先, 按序)**: ①打印磁盘文件 mtime + 材质各通道连线 dump(证明"同一个文件"且该接的通道都在); ②从当前磁盘文件重渲同机位; ③同文件仅换光照 A/B(复现用户视角); ④给完整路径+时间戳, 让用户 File > Revert 重载, 视口着色切"渲染(Rendered)"(或 F12) —— 材质预览模式天然平软, 不是文件缺陷。
**硬规则**: 任何"用户观感缺陷"先用单变量 A/B 复现其视角再下结论; 修复效果也单变量量化后再汇报。**潜在问题 ≠ 主因** —— 没量化的因果断言会被用户一验证就打回(本项目: 把法线缺失断言为"五官糊"主因, 实测接通前后差异很小; 正确措辞="该接(产物卫生), 但可见主因是光照")。
**分辨率天花板如实说**: 低模+4K vs 高模+8K, 特写必有亚毫米细节上限(眉发/唇纹), 是数据量差异不是缺陷, 别承诺消除。要治的直杠杆 = 烘焙分辨率提档(4K→8K: 面部等效密度×2≈追平源), 但属用户决策 —— 先报代价(烘焙时长≈×4、贴图体积≈×4、GLB增大)再动手, 不擅自改。

## "和上游产物比, 五官变形了"类指控: 同机位 + 标志点定量(实测)

跨版本对比是读图工具的翻车区: 同一对图两次读图得出过相反结论("五官全变形" vs "无变形")。**settle 只有一条路: 同机位同光照同分辨率渲染 + 标志点数值。**
- 渲染: 两份 blend 各挂同一正交相机(平视, ortho_scale 固定)、同一太阳+世界光、同分辨率 → 两张图(现成脚本 `scripts/stage_render_compare.py`);
- 量化(全部现场算, px→mm 用 ortho_scale/分辨率换算):
  ① 面部轮廓行宽: 5 个高度(30/40/50/60/70%)的肤色行左右边界逐行比;
  ② 嘴部暗带 y 范围(下半脸 暗且 r>g>b 像素的分布);
  ③ 特征定点: 眼带内左右半各自最暗像素的位置+RGB(虹膜/瞳孔);
- 实测合格例: 轮廓 5 行差 ≤5px(≤1.2mm)、嘴带同位置、虹膜四点同值 → **零变形**; 真实差异只剩清晰度/细节量(见"分辨率天花板")。用户视角的"全变了"多来自: 两视口缩放/透视/光照不同 + 细节糊掉后的观感放大。
- 对比前先确认"上游那个文件是哪个": 同阶段常有多份产物(如 原始修复高模 vs 已切眼窝的高模——眼球来源可能根本不同: 贴图上画的眼睛 vs 眼球资产), 拿错文件会把资产差异误判成变形。

## 文件存在性切换行为 + 替换件溯源(实测)

04 的 FIXED_TEX 机制: `01高模修复/输出/01_original_tex_fixed.png` **存在即自动替换**高模贴图, 不存在则用内嵌原图 —— 行为由文件存在性切换。核对时: ①打印实际读取的文件名+尺寸, 与源做像素 diff 量化改动 footprint(实测 0.29% = 仅眼窝区); ②警惕**同名多版本历史文件**(用户目录里曾发现同名文件与现用源差异 19.7% = 历史版本, 管线未读但极易混淆) → 替换件须注明生成脚本与输入源; 发现同名历史件只报告请用户处置, 不假定它被使用、也不顺手删。

## "把整个流程检查一遍"类审计的清单(user 会这样提)

1. 通读全脚本, 专找三类高危: **存在性切换**(文件在/不在改变行为)、**临时断开**(导出/烘焙前断开的节点/连线是否在保存产物前复原)、**临时文件**(坏中间态会不会占用最终产物名);
2. 每个修复/掩膜量 footprint + 用已知探测点验证掩膜覆盖(见眼窝节);
3. 产物 blend 程序化 dump 材质通道连线(见法线节);
4. 命名口径核验(如"未调整"实际含哪几步 —— 本项目 = 烘焙+眼窝皮肤化, 非绝对纯烘焙);
5. 输出按【本轮已修 / 确认无问题 / 环境性发现(请用户定)】三段写, 存档方案md。

## 指标盲区(已知)
三项指标(未填充/脏块/密度CV)对"衣物-皮肤边界渗出环"不敏感(脏块值轮次间几乎不变) → 边界质量要另看渲染复检; 渲染近距下的衣物边缘"锯齿"要区分: 深色污染=烘焙渗出(要修), 多边形棱角=低模几何(正常)。
