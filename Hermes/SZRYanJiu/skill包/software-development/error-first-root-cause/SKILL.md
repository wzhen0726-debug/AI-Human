# 错误处理流程：先找根因，再决定动作

## When to Use

任何多步流程（3D管线、脚本、构建、部署）出现错误/异常/不符预期时，**动手修改之前**先按本流程走。发现"该用的工具没用"（如已购插件没被使用）时同样适用。

## 核心原则（用户明确要求，2026-08-25）

> 出现错误时，不要先想着修改错误，而是先判断**流程中错误产生的原因**，再尝试在**保证流程正常推进**的情况下，**从源头避免错误**。如果不能避免，再**找我做取舍**，或者开始正式修复错误。

## 步骤

1. **定位根因，不改表象**
   - 错误出现在哪一步？是这一步的逻辑错，还是上一步的输入就错了？
   - 用数据/日志/可视化确认，不要凭猜测改。
   - 区分：是「本步写错」还是「上游污染了本步」。

2. **判断能否从源头避免**
   - 如果是流程设计缺陷（如测试代码污染交付文件、坐标空间约定不一致），改流程/约定，而不是每次事后补救。
   - 源头修复 = 让这类错误以后不再发生。

3. **无法避免 → 找用户取舍**
   - 有多个修复路线、各有代价时，列清楚选项和代价，让用户选。
   - 不要擅自选一个重方案直接做。

4. **正式修复**
   - 确认路线后，从源头修，并验证修复后整条流程能正常推进（不是只修这一个点）。

## 反例（禁止）

- ❌ 看到姿态错了，直接 `rotation_euler = 0` 清掉，不管为什么会有旋转。
- ❌ 看到眼珠朝下，直接转一下眼球，不管父级坐标空间为什么错。
- ❌ 报错就打补丁绕过，不查报错来源。

## 正例

- ✅ 发现交付文件自带姿态 → 查到是「弯肘测试后没清 pose + 测试与交付未隔离」→ 改流程：测试在临时副本做，交付文件永远干净。
- ✅ 眼珠朝向错 → 查到 `parent_type=BONE` 让子对象继承骨骼 tail 方向 → 源头改用 OBJECT 父级或权重绑定。

## 相关

- 本原则同样适用于：发现「该用的工具没用」时（如买了 Auto-Rig Pro 却手写绑定），先承认并评估该工具，再决定路线。
